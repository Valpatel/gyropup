# Inspect the imported assembly, including names and material assignments

On 2026-10-29, PR67's `8b86e7f` review STEP loaded 27,186 triangles but displayed entirely in one color. The exporter had combined the base, PCB, screws, inserts and connector reservations into one compound. Its comment described labelled geometry, but the actual imported model could not distinguish completed parts from reserved space. The shared viewer already preserved source names/colors; the exporter was losing them.

The correction exports a named, colored assembly. At `4a07c11` / assets `d771603d80e3988b4579`, independent Chrome/WebKit checks observed 30 member identities, seven colors and 27,158 triangles at 320×568, 390×844 and 1440×1000. The eight screws, eight inserts and four explicitly named C2 reservation members remain distinct. The page describes reservations and leaves readiness false. This is a bounded inspection assembly, not full BOM or physical qualification.

The persistent `npm run test:carrier-inspection` follows the native document→Preview→viewer→document path, hashes the served original against its committed receipt, checks Mermaid and member-specific materials, and exercises camera views/fine wheel/framing. Negative controls mutate the actual browser scene to lose colors, swap colors between parts, hide an insert and remove a screw; the same observation path rejects them. This catches appearance loss even when an STL/STEP file and triangle count exist.

A single earlier WebKit ready-only wait timed out without preserving the terminal state. Three independent exact-sequence reproductions loaded the unchanged file in 3.67–3.86 seconds, without worker/console/network errors; its cause remains unknown. The new harness waits for ready **or** error/cancellation and always saves failure state, requests and a capture. It also waits for the returned document diagram before beginning the next navigation, so the test does not abort its own in-flight Mermaid fetch. No speculative reader-code change was made.

Corrective rule: inspect the real consumer artifact, not merely the producer's intent or a number of distinct colors. Materials must remain attached to the correct members. Keep diagnostic failure evidence even when later attempts pass, and do not turn an unqualified reservation into apparently finished hardware through presentation.

On 2026-10-29, the C3 support author and independent visual reviewer independently chose the same temporary output directory. Their JSON report names were distinct, but some screenshot names could overlap; unique screenshot ownership could not be established. The reviewer repeated its inspection in a separately named directory. No source, model hash or programmatic result changed. The shared screenshots must not be presented as uniquely authored evidence. The persistent harness now allocates a fresh random default directory; an explicit `TEST_OUTPUT` must use an agent/run-specific prefix. Candidate names also distinguish reports and screenshots within a run. CI's existing `/tmp/gyropup-*` evidence glob retains these directories.

A further independent review found that traversing hidden meshes and only clicking camera buttons allowed hidden mounting hardware and listener-free view buttons to pass. The harness now observes renderable scene members (visible ancestors, active draw ranges, visible/nonzero-opacity materials and nondegenerate bounds), checks each preset's camera direction and requires Fit to restore the pre-wheel framing distance. Hidden-object, hidden-material and zero-opacity corruptions are explicit scene controls. This establishes render eligibility, not that every face is unoccluded from one camera pose. These are test-coverage corrections; the reviewer did not find those defects in the current viewer.

## A later passing import does not erase an intermittent reader error

On 2026-10-29 the hosted WebKit C3 run at production `874f961` passed 320px, then the 390px load reached the viewer's error state with `access to a null reference (evaluating 'invoker(fn,arg0Wired,arg1Wired)')`. HTTP/request/page-error arrays were empty because the STEP worker caught the parser exception and surfaced a Retry file control. Receipt: `/tmp/gyropup-navigation-webkit-final-N0J7lO/webkit-c3-support-report.json`. The unchanged source STEP SHA256 was `7a1ee25ffefbbf961b7aa83b17c89455ecfa42e8b4191c9d17b24821151c4824`; wrapper version was occt-import-js 0.0.23, test runner Playwright 1.56.1.

A fresh isolated WebKit C3 run passed all three widths (`/tmp/gyropup-navigation-webkit-c3-repro-m9meX1`). Independent review also observed an error state in a fresh context, but that first probe did not retain its exact message; its instrumented follow-up passed both tested cases. These results do not identify a cause or establish uniformly successful imports. [Issue #101](https://github.com/Valpatel/gyropup/issues/101) retains the unresolved investigation. The navigation-only correction in PR #100 changes no parser code and does not fix this reader issue.

Corrective rule: assert the viewer's terminal state, retain caught worker errors and their original asset/version, and report intermittent failures even when a fresh run passes. Do not substitute a successful retry for an explanation, add an implicit retry to make validation pass, or equate an empty page-error list with a working reader. Cause remains unknown; no file, browser engine or resource-limit diagnosis is established by this evidence.
